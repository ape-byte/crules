# 与 Jint 的对比测试

本文解释原生 C#、Jint、CRules 三方对比的调用与数值口径，并拆开 Jint 的输入方式。三方主表及重构前后判断统一见 [性能报告](%E6%80%A7%E8%83%BD%E6%8A%A5%E5%91%8A.md)。数据来自 2026-11-10、CRules `99dda85`，不是当前所有新功能的性能复测。

## 1. 三方是什么

| 实现 | 输入与准备 | 执行 |
| --- | --- | --- |
| 原生 C#（Roslyn 构建） | benchmark 源码由 .NET SDK 构建；同一规则展开成静态方法 | NoInlining 方法，通过 Func 委托调用 |
| Jint 4.17.0 | JavaScript，按测量入口准备函数/AST，每进程复用一个 Engine | CLR 对象函数调用、SetValue + Evaluate 或 JSON 函数调用 |
| CRules | C# 风格有限函数体，准备一次，类型检查、审计并组合表达式树 | JIT 强类型委托，重复执行 |

这里没有运行时 Roslyn CSharpScript 组。生产 CRules 核心不依赖 Roslyn 或 Jint；Roslyn 仅用于语义参照测试，Jint 仅用于基准。

三方主表固定 Jint 函数 + CLR 入口，不能在不同场景中挑选不同 Jint 入口拼成一个“Jint 性能”。其他入口完整列在下面。

## 2. Jint 不同输入方式

单位 **ms / 100,000 次**。每次新建随机上下文，执行并逐项校验，排除准备；CRules/原生各 5 进程中位数，Jint 各 3 进程中位数。

| 场景 | 原生 C# | CRules | Jint 函数 + CLR | Jint SetValue + AST | Jint 函数 + JSON |
| --- | ---: | ---: | ---: | ---: | ---: |
| S1 小 / 简单 | 25.76 | 24.05 | 378.05 | 411.68 | 1,039.37 |
| S2 小 / 100 变量 | 39.07 | 39.72 | 7,372.23 | 7,626.14 | 4,986.96 |
| S3 小 / 100 变量 + 分支 | 37.49 | 39.68 | 8,408.18 | 8,359.71 | 5,204.60 |
| S4 大 / 简单 | 1,020.87 | 961.79 | 1,447.91 | 1,575.43 | 21,005.90 |
| S5 大 / 100 变量 + 分支 | 1,000.84 | 988.62 | 25,798.13 | 22,893.74 | 33,485.40 |

所有 Jint 模式均在进程内复用 Engine，不是每次计算新建 Engine。JSON 模式额外包含 JSON 输入转换，CLR 包装在属性访问密集时也有额外成本；不能凭单一场景认定任一输入方式总是更快。

S4 中上下文构建已占主要成本，Jint CLR 与 CRules 的完整循环耗时比只有约 1.51×。S2/S3 的大量变量与属性访问则呈现不同成本。场景规模会改变收益，表中倍数不是通用保证。

## 3. 分配口径

单位 **B / 次完整循环**，包括构建上下文；不是引擎常驻内存。

| 场景 | 仅构造上下文 | 原生 C# | CRules | Jint CLR | Jint JSON |
| --- | ---: | ---: | ---: | ---: | ---: |
| S1 | 384 | 384 | 384 | 2,980.79 | 16,584.59 |
| S2 | 384 | 384 | 384 | 16,716.27 | 27,933.52 |
| S3 | 384 | 384 | 384 | 17,519.14 | 28,253.52 |
| S4 | 17,304 | 17,304 | 17,304 | 19,900.60 | 83,697.39 |
| S5 | 17,304 | 17,304 | 17,304 | 83,049.93 | 95,366.56 |

这批 CRules 简单强类型计算没有在上下文构造之外观测到额外的每次分配，不等于集合/对象结果、Type 入口、动态数据或 AOT 都零分配。工作集还包含启动、预热和准备，不能把峰值工作集当成 Engine 对象大小。

## 4. 准备和生命周期不能混比

固定输入 BDN 短基准中：CRules 完整解析/审计/委托编译约 1.149 ms；Jint 仅 AST 准备约 0.015 ms；Jint 解析、新建 Engine 与执行约 0.082 ms。这三项产物和工作量不同，不能把它们解释成同等编译任务的胜负。

JSON 宿主基准中，CRules 的 JSON 输入/执行/输出约 2.042 μs；Jint 新 Engine + JSON + 冻结约 27.136 μs。它们是明确的宿主场景，不是“复用 Jint Engine 每次必然花费这些时间”。完整循环主表不包含每次新 Engine。

原生 C# 在 benchmark 构建阶段编译，未单独测运行时准备成本，不能为其填写“编译耗时 0”。规则更新频繁时应另测真实加载周期，而不只看热调用。

## 5. decimal 与 JavaScript Number

CRules/原生 C# 可直接使用 decimal；Jint 中普通 JavaScript Number 是二进制浮点。比如普通 JS 的 `0.1 + 0.2` 与 C# `0.1m + 0.2m` 不具有相同的十进制表示语义。

本次五场景主测使用安全整数/定点表示和逐项结果校验，**没有额外向 Jint 叠加十进制 helper**。这是为了减少精度实现方案对主测的干扰，不代表任意 decimal 算法可以直接改成 Number。

独立 decimal 微基准才采用十进制字符串 helper：原生委托 40.742 ns、CRules 委托 42.673 ns、Jint helper 1677.389 ns。Jint 结果包含字符串转换与跨边界调用，不能作为“Jint 原生 Number 算术慢多少”的结论。

如果规则必须保证某种十进制/定点语义，先固定范围、舍入和表示，再验证结果一致。decimal 也不是任意精度，CRules 的 DecimalOnly 会拒绝浮点子树，并不会自动修正不合适的输入或算法。

## 6. 执行模型差异

| 关注点 | CRules | Jint |
| --- | --- | --- |
| 规则形态 | 明确的 C# 风格函数体子集 | 本测试执行 JavaScript |
| 参数 | 声明输入和返回签名，准备阶段绑定 | 本测试使用 CLR 包装、SetValue 或 JSON |
| 结果与错误 | 编译诊断 + .NET 运行异常 | JavaScript/宿主运行异常及输入转换成本 |
| 扩展 | 已公开且通过审计的宿主成员 | 本测试按具体 CLR/JSON 入口配置 |
| 生命周期 | 编译后复用 executable | 此处复用 Engine；独立宿主测试另测新 Engine |

这张表说明本项目的对比口径，不是两库全部功能或安全边界的评测。不能用有限语法执行器的性能结果证明它可替代完整 JavaScript 语言需求。

## 7. 怎样复测

1. 固定原生方法、CRules 代码、JavaScript 代码及输入表示，先逐项验证输出/异常。
2. 分别测准备、上下文构造、完整调用和预分配输入热调用，不混入计时外的不同工作。
3. Jint 明确选择复用 Engine、CLR/SetValue/JSON 入口；需要每次隔离时另建测试组。
4. 使用独立进程和足够预热，记录机器、运行时、实际程序集版本、GC、分配、均值/中位数与区间。
5. NativeAOT 解释执行单独测量，不沿用 JIT 结果；Roslyn CSharpScript 如需比较也必须另加真实测试组。
