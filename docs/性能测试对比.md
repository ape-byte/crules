# CRules 与 Jint 性能及内存对比



测试日期：2026-11-09。本文根据仓库中已完成的测试记录整理，没有为本次文档更新重新测量。适用范围是 .NET 10 JIT、下述固定工作负载，以及安全整数／定点数值语义。



## 1. 已测结论



规则准备一次并反复调用、每次新建小 context 的简单场景中，CRules 十万次总耗时为 **106.88 ms**，较快的 Jint 单例入口为 **754.10 ms**，耗时比约 **7.06×**，即 CRules 耗时减少约 **85.8%**。对应本次完整循环的平均成本约为 **1.07 μs/次、7.54 μs/次**，包含随机 context 构建、输入传递和结果校验。



小 context 的 100 变量复杂规则，选取各场景较快的 Jint 单例入口后，耗时比约为 **47.15–61.62×**；大 context 简单规则则只有约 **1.52×**。这些场景说明输入构建、转换和表达式复杂度会改变整体收益，不能合并成统一倍数。



当前实现适合编译后重复使用规则。每次重新编译的成本较高，在本次准备成本测试中明显慢于 Jint 单例逐次解析文本，具体数值见第 7 节。



完整交互图表见 [离线 HTML](performance/2026-11-09/business-100k/index.html)，详细逐实现表格见 [本轮生成分析](performance/2026-11-09/business-100k/分析报告.md)。

小 context 包含请求、价格和 8 个指标，前 16 份样本 JSON 大小均值约 **268 B**，实际构建分配约 **384 B/次**。



大 context 包含 128 个指标、64 个八字段明细对象、16 个随机标签、32 个 data 字段，以及每次新分配的 4096 字符 payload。前 16 份样本 JSON 大小均值约 **11.69 KiB**，实际构建分配约 **17,304 B/次**。JSON 大小用于描述输入，不等于托管对象大小。



| 场景 | context | 局部变量 | 条件节点 |

| --- | --- | ---: | ---: |

| S1 | 小 | 1 | 1 |

| S2 | 小 | 100 | 0 |

| S3 | 小 | 100 | 32 |

| S4 | 大 | 1 | 1 |

| S5 | 大 | 100 | 32 |



100 个变量是顺序依赖链，后一个使用前一个，返回值消费最终的 v99。复杂规则包含 8 组 if/else-if/else 及嵌套 if，共 32 个条件节点；随机 flags 和 Vip 覆盖不同分支。大 context 复杂规则还读取指标和明细字段。完整源码与首份输入样例见 [rules 目录](performance/2026-11-09/business-100k/rules/)。



数值计算使用有界整数／定点单位，输出远低于 JavaScript 安全整数上限 2^53。每次结果都与独立循环参考实现生成的期望值比较，避免给 Jint 叠加 decimal 字符串 helper 的转换负担。本轮不证明任意 decimal 算法与 JS Number 等价。



## 3. 实现与计时边界



| 原始模式名 | 生命周期与入口 |

| --- | --- |

| BuildOnly | 只构建随机 context，作为输入构建基线；测 S1、S4 两种形状 |

| NativeReference | 原生 C# 独立循环参考算法，用于正确性和端到端基线 |

| CRules | 准备一次，复用一个强类型编译委托，每次传入新 context |

| JintSingleton | 同一个 Engine，提前定义函数并解析 decide(ctx)，每次 SetValue 更新 CLR context 后 Evaluate |

| JintClr | 同一个 Engine，提前取得函数，每次通过 CLR 参数调用 |

| JintJson | 同一个 Engine，提前取得函数，每次序列化 context、JSON.parse 后调用 |

| JintIsolatedJson | 每次新建 Engine，复用已准备的 AST，并包含 JSON、深冻结、语句／内存／递归限制 |



三种单例模式均连续复用同一个 Engine 完成预热和十万次计时调用。隔离模式的成本单列，不能用于代表普通单例 Jint。单例均串行执行，本测试没有测并发共享 Engine 或引擎池。



每个主测组合在独立进程内准备一次，预热 2000 次后强制 GC，再测量完整循环。随机数据与 context 对象在计时内逐次创建，没有提前生成十万个对象或 JSON。期望结果数组在计时前生成；逐项比较和校验和更新计入主循环。



主测试原批次旋转实现顺序；SetValue 单例入口按补充要求在之后另批测量三轮，算法、种子及引擎版本不变，批次信息见 [singleton-supplement.json](performance/2026-11-09/business-100k/singleton-supplement.json)。由于批次不同且轮数有限，不能消除所有机器负载、温度和调度影响。



统计值为三轮中位数，没有扣除空调用或构建基线。只构建 context 与执行规则的不同进程也有波动，不能机械相减得到“精确引擎耗时”。



## 4. 复用规则的十万次耗时



以下单位为 ms，包含每次构建随机 context，排除首次规则准备。表中的耗时比选择三种单例模式中耗时较低者。



| 场景 | CRules | 单例 SetValue | 单例函数 CLR | 单例函数 JSON | 较快单例 / CRules |

| --- | ---: | ---: | ---: | ---: | ---: |

| S1 小 context、简单规则 | 106.88 | 754.10 | 839.04 | 1,901.45 | 7.06× |

| S2 小 context、100 个依赖变量 | 104.44 | 6,124.79 | 6,155.10 | 4,924.04 | 47.15× |

| S3 小 context、100 个变量和 32 个条件节点 | 82.13 | 6,133.28 | 7,917.12 | 5,060.52 | 61.62× |

| S4 大 context、简单规则 | 1,226.71 | 1,858.94 | 1,908.21 | 12,920.13 | 1.52× |

| S5 大 context、100 个变量和 32 个条件节点 | 1,208.23 | 15,140.57 | 17,350.93 | 17,372.66 | 12.53× |



S2、S3 的 JSON 单例入口更快，但分配量高于 CLR 入口；入口选择需要同时考虑时间和 GC 成本。各场景的工作量不同，S3 与 S2 的中位数大小关系也受 JIT、CPU 和测量波动影响，不能据此推断增加分支会让程序更快。



隔离模式及原生 C# 参考路径单独列出：



| 场景 | 原生 C# 循环参考 ms | CRules ms | Jint 每次新建 Engine 隔离 ms |

| --- | ---: | ---: | ---: |

| S1 | 70.81 | 106.88 | 6,831.65 |

| S2 | 181.84 | 104.44 | 33,139.28 |

| S3 | 182.57 | 82.13 | 36,151.03 |

| S4 | 1,286.53 | 1,226.71 | 77,864.19 |

| S5 | 1,172.82 | 1,208.23 | 133,000.06 |



原生 C# 参考实现使用循环，生成规则使用展开的局部变量链，优化机会不同。这一参考值不代表原生 C# 的性能上界，也不能据此声称 CRules 优于等价优化的原生代码。早期原生直接调用／委托的标量微基准另见 [早期微基准报告](performance/2026-11-09/性能测试报告.md)，其计时范围与本表不同。



## 5. 分配、GC 和进程内存



下表为每次调用的托管分配量，单位 B/次，包含 context 构建。每项取对应三轮分配量的中位数后除以 100,000。



| 场景 | CRules | 单例 SetValue | 单例函数 CLR | 单例函数 JSON | 隔离 Engine |

| --- | ---: | ---: | ---: | ---: | ---: |

| S1 | 384.00 | 3,189.21 | 2,937.53 | 16,556.95 | 65,613.47 |

| S2 | 384.00 | 16,880.11 | 16,654.52 | 27,888.91 | 503,538.56 |

| S3 | 384.00 | 17,682.85 | 17,457.75 | 28,209.50 | 552,186.39 |

| S4 | 17,304.00 | 20,072.48 | 19,843.72 | 83,650.79 | 334,193.39 |

| S5 | 17,304.00 | 83,210.56 | 82,985.93 | 95,319.14 | 1,002,942.87 |



CRules 在这些有界整数标量 JIT 用例中的分配量与相应 context 构建基线一致，100 个局部变量没有产生可观察到的额外逐次托管分配。这个结果不涵盖 LINQ、宿主工具返回对象或其他会分配的规则。



下面并列 CRules 与常见 SetValue 单例的累计分配、GC 次数和峰值工作集。GC 次数取各代计数的三轮中位数；各列是独立统计值，不要求来自同一轮。



| 场景与实现 | 累计分配 MiB | Gen0/Gen1/Gen2 | 峰值工作集 MiB | 强制 GC 后堆 MiB |

| --- | ---: | ---: | ---: | ---: |

| S1 CRules | 36.62 | 6/0/0 | 46.55 | 1.76 |

| S1 Jint 单例 SetValue | 304.15 | 50/0/0 | 52.46 | 2.41 |

| S2 CRules | 36.62 | 6/0/0 | 49.67 | 1.82 |

| S2 Jint 单例 SetValue | 1,609.81 | 269/0/0 | 54.24 | 3.16 |

| S3 CRules | 36.62 | 6/0/0 | 49.79 | 1.86 |

| S3 Jint 单例 SetValue | 1,686.37 | 281/0/0 | 53.63 | 3.33 |

| S4 CRules | 1,650.24 | 275/0/0 | 51.05 | 1.76 |

| S4 Jint 单例 SetValue | 1,914.26 | 319/0/0 | 53.68 | 2.44 |

| S5 CRules | 1,650.24 | 275/0/0 | 53.06 | 1.88 |

| S5 Jint 单例 SetValue | 7,935.58 | 1326/1/0 | 56.81 | 3.70 |



S5 中，CRules 与 Jint 单例 SetValue 每次约分配 17,304 B 和 83,211 B，累计分配相差约 4.81 倍；峰值工作集约为 53.1 MiB 与 56.8 MiB，差距小得多。减少分配主要缓解 GC 和分配器压力，不能将这一倍率直接换算为进程驻留内存倍率。



累计分配统计十万次过程里产生的所有托管对象，已经回收的对象也计入。峰值工作集覆盖进程启动、准备、预热和计时阶段。强制 GC 后的堆仍包含期望值数组、规则，以及被测量代码保留引用的执行器／已 Dispose 引擎对象，不能当作单独引擎大小或泄漏证明。准备成本补测只记录分配与 GC，没有单独采集进程工作集。

## 7. 每次重新准备的独立测试



这一部分实际执行简单规则 **1000 次**、100 变量规则 **200 次**，每种组合三轮，没有外推成十万次。所有路径包含新建 context 与一次计算。



CRules 每次构建新执行器，完成类型绑定、审计、表达式树组合和编译。单例 Jint 每次 SetValue 后 Evaluate 规则文本，复用 Engine，但逐次重新解析。另列每次构建 Engine 的两种路径。



新执行器路径还包含测试规则文本的生成；单例文本路径提前生成规则文本。因此这一测试表示具体使用方式的准备加执行成本，不是纯解析器的严格等工作量微基准。各组合在同一准备测试进程中依次执行，不采用主测试的独立进程隔离，不能与主表混为同一种实验设计。



| 场景 | 实际次数 | CRules 总 ms | 单例文本解析总 ms | 新 Engine CLR 总 ms | 新 Engine 隔离 JSON 总 ms |

| --- | ---: | ---: | ---: | ---: | ---: |

| S1 | 1000 | 3,932.62 | 130.50 | 348.92 | 919.74 |

| S2 | 200 | 8,142.22 | 355.44 | 265.95 | 284.00 |

| S3 | 200 | 18,193.09 | 1,083.84 | 651.61 | 798.80 |

| S4 | 1000 | 2,588.45 | 114.22 | 274.30 | 2,218.52 |

| S5 | 200 | 20,020.27 | 531.76 | 381.94 | 672.64 |



以 S5 为例，200 次重新编译加执行约需 20,020 ms，Jint 单例文本解析加执行约需 532 ms。重复调用 Compile 会失去规则复用的主要收益，宿主应在加载或更新规则时编译并保存句柄。



## 8. 波动、验证及适用边界



S5 的单例 SetValue 三轮耗时约为 **14.13–54.63 秒**，中位数约 **15.14 秒**。HTML 保留每轮原始值、范围和波动提示。三轮样本不足以给出正式容量、尾延迟或稳定倍率承诺。



主测共 96 条独立进程记录：5 场景 × 6 计算实现 × 3 轮，加上 2 种 context 构建基线 × 3 轮。共 **900 万次计算逐项校验一致**，另有输入和结果滚动校验和。准备成本共有 60 条记录。已有回归记录为 **51 项独立核心测试通过**，见 [验证记录](validation/2026-11-09/business-workloads/verification.json)。



本轮没有覆盖结构体 context、并发引擎池、长时间稳态负载、真实服务尾延迟、任意 decimal 算法或 NativeAOT 性能。NativeAOT 的实际功能验证和能力限制见 [专门文档](NativeAOT支持与限制.md)。结构体收益讨论仍属于待实验判断。



## 9. 复现步骤



在仓库根目录执行以下命令，使用新的输出目录保存本机记录。测试会包含较慢的隔离 Engine 和重新编译路径，运行时间明显长于普通单元测试。需要 .NET SDK 10.0.401 同特性带、Python 3 标准库；完整锁文件要求见仓库 README。



```powershell

dotnet restore benchmarks/CRules.Benchmarks --locked-mode

dotnet build benchmarks/CRules.Benchmarks -c Release --no-restore

dotnet run --project benchmarks/CRules.Benchmarks -c Release --no-build -- --business-suite docs/performance/local-business-100k 100000 3

dotnet run --project benchmarks/CRules.Benchmarks -c Release --no-build -- --business-prepare docs/performance/local-business-100k

python benchmarks/reporting/build-business-report.py docs/performance/local-business-100k

```



生成器会检查主记录数量、次数、规则哈希及校验和，然后生成 `index.html`、`分析报告.md`、`report-data.json`、`measurements.csv` 和 `summary.json`。当前脚本针对五场景、十万次、三轮的完整套件；改变规模时需要同步调整报告校验约束。



若需要将本机 CPU 信息纳入新报告，可在生成 HTML 前执行：



```powershell

Get-CimInstance Win32_Processor |

    Select-Object Name, NumberOfCores, NumberOfLogicalProcessors |

    ConvertTo-Json |

    Set-Content -Encoding utf8 docs/performance/local-business-100k/cpu.json

```



当前 `--business-suite` 已包含三种 Jint 单例入口。`--business-singleton <输出目录>` 用于对旧批次补测 SetValue 入口，会替换该目录中此模式的记录，完整重跑无需额外执行。



如需另行运行 BenchmarkDotNet 微基准：



```powershell

dotnet run --project benchmarks/CRules.Benchmarks -c Release -- --verify

dotnet run --project benchmarks/CRules.Benchmarks -c Release -- --filter '*' --job short --exporters json

```
